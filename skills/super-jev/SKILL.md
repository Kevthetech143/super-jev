# Super Jev
Run from this skill directory: `python3 dispatch.py <tool> ...` (or `ask.py` directly, as shown below). Use the user's original request and relevant context; keep backend names and setup mechanics out of ordinary replies. **Remember or one-off:** connect what agents will search again without knowing where it is (notes, lessons, decisions, a code library; `super-jev-connect`), then `ask.py` finds it. Check anything you already have in front of you directly, with nothing connected: new code, a worker's report, a pasted page: `python3 dispatch.py check FILE [FILE ...] --claim "statement"` (a unified diff is judged as code) or `python3 dispatch.py verify REPORT --worktree DIR`; a shelf lookup about files that are not connected answers NOT FOUND. A one-off answer worth keeping becomes a fact: `ask.py --principal YOUR_AGENT --add "question" "answer" --source FILE`.

## Commands

| Command | Example | What it does |
|---|---|---|
| `ask` | `python3 ask.py --principal YOUR_AGENT "question in your own words"` | Cache first, then every connected pointer at once: routing requests and file checks use the batch CLI; compatible routing questions share Jev calls, while ordinary source checks use independent file evidence (passages within a file share one evaluation; input limits split automatically; `SUPERJEV_BATCH_JEV=0` disables CLI batching); word search adds the files whose text matches the question to the ones routing picked, so a note routing missed is still read; open the top file before answering. `--approve` a good hit so the next ask of the same question is instant (a saved answer lasts until its source file changes; there is no clock expiry) (new explicit approvals record `principal:NAME`, not an assumed human; existing labels stay intact, missing historical identity is `unknown (legacy)`; principal labels are not authentication) (add `--rank N` or `--file PATH` to approve a different listed candidate than the top one, possible-tier included, from that candidate's own pointer, quoting only that exact file: its opening line plus its line that best matches the answer, cited from the file's own reviewed lines; dates and numbers break word-match ties, and replay shows up to 120 characters of the best saved supporting line; memory's separate search never decides whether a file ask() ranked can be saved); `--add` a fact with no file (it gets the secret scan only and is marked `no source file`; with `--source FILE` the claim check runs on that file, and a `--source` that does not exist is refused; every save path -- `--approve`, `--answer`, `--used`, `--confirm-pick`, `--add` -- runs the same secret scan and claim check, CLEAN at 0.80 or higher; "the same question" means the same words after lowercasing, collapsing spaces and dropping trailing punctuation, nothing fuzzier; a hit prints `saved answer, from FILE, saved DATE`); after using a listed file, leave a trail with `--used last --rank N --answer "..."` (every 5 picks the claim checker saves CLEAN ones as `agent-pick+check`; `--pending-picks` lists unsure ones AND refused ones (REJECT/TIME_SENSITIVE/stale/secret-held), each with its reason, to `--confirm-pick`/`--drop-pick` -- a refused pick no longer vanishes silently, see [verified reuse](references/verified-reuse.md)); `--miss` when a saved answer is wrong (it removes the answer and exits 1 if nothing was saved) or the answer was found elsewhere, naming the file by its full path (a path makes the miss a scorecard test; free text does not). A saved answer whose source file changed (any save path) is withheld (STALE, said in the reply) and the question falls through to a fresh live search; a saved `--add` note whose source changed is also skipped by live search. Save it again after checking the file (`--approve`, or `--add --replace-entry`). Every ordinary ask starts with exactly one line, `OUTCOME: <kind> - <reason>[; next: <one command>]`, computed from the whole search: `found` (at least one file or skill suggestion; the file count is the ranked files only, up to 5, and skill suggestions are counted on their own label, e.g. `found - 5 files; 2 skill suggestions`; `partial: N sets not searched` when a set failed or is stale; `(unconfirmed: content check failed)` when the content check failed and the files are only routed, unread candidates: still exit 0, read them), `not-found` (complete search, no file), `needs-setup` (no file, and a set was stale, unprepared or skipped: a partial search is never a complete not-found), `not-supported` (empty or over-long question) or `error` (no file, and execution failed). Exit codes match: found 0, not-found 1, not-supported 2, error 3, needs-setup 4 (`--claim` keeps its own verdict lines and exit codes). Errors still print per pointer, never hidden as no-candidates; a stale pointer's line prints every time (never dropped) with the exact refresh command (roots and every principal included) to run as-is. Bench datasets under `.local/retrieval-datasets/` are never listed. Ordinary retrieval uses one source-evidence rule for every question: the existing content check asks of each file, "does this file state the answer to the question?": retain text that states the requested fact, including a component needing another source or calculation. A file about the right subject or topic that states neither the requested property nor a necessary input to it, and redirects, are rejected, and a rejected file is never reported as found. Source discovery explicitly permits necessary components and ranks up to five candidates per pointer, plus word-matched files, without an absolute cutoff on relative routing mass; it cannot rescue rejected content. Poorly described files can still be missed when neither routing nor the word match picks them. Accepted evidence ranks by content, with routing used only to break ties. File names do not override the content result. Up to five files are returned; read the relevant files and do the reasoning yourself. Unfinished checks stay explicitly inconclusive, after completed evidence. `not-found` means not found, not absent: say it may still exist and offer a by-hand search. Notes over 12,000 characters, up to 250 KB, are supported and read in sections (bigger ones are outside the contract), so retrieval can miss facts; strong routing does not rescue a rejected section. Person-scoped filtering and reviewed-source admission still apply. Ordinary retrieval does not run a single-best-answer picker; `--claim` keeps its separate support/contradiction judge. See [source retrieval](references/source-retrieval.md) for the scope and limits. |
| `navigate` | `python3 dispatch.py memory --input NAV.json` (a JSON file path, not inline JSON: `{"action":"navigate","pointer":"POINTER_ID","principal":"YOUR_AGENT_NAME","question":"..."}`) | Lower-level call `ask` wraps: searches one connected pointer's catalog for candidate files. Open the top file; a high score never proves it's in scope. |
| `skills` | `python3 dispatch.py skills --request "..."` (or `--request-file REQUEST.json`) | Skills connector: discover candidate skills from configured trusted local roots; suggestions never execute them. `status: error` (exit 2) carries the real cause; `fallback` or local-source suggestions are unverified guesses, not matches. |
| `ask --claim` | `python3 ask.py --principal YOUR_AGENT --claim "statement" [--claim "statement2" ...]` | Read evidence reaches the claim judge even when the answer filter rejects it; contradictory evidence is retained. Is a statement true by your own files, with no FILE to name: one lookup per statement, and the same listwise Jev call judges each shown file (supports / partly / contradicts / does not state) and picks the line that shows it (no extra call). Prints first: `TRUE`/`FALSE` (only at >= 0.90, with proof file, date and line: you may answer from it), `CONFLICT` (sure files disagree, newest first: read both), `PARTIAL`, `UNSURE` (read the listed files) or `NOT FOUND` (in the files read: it may still exist; follow the miss lines), then the files found (a file the judge surely reads as not stating the statement is never listed). A sure TRUE/FALSE is saved and answers the same statement instantly until its proof file changes. `--claims-file FILE` checks one statement per line; a statement that cannot be checked prints `could not be checked` and the rest still run (exit 3). Use it to check facts in a draft before sending, and a worker report's claims (with `dispatch.py verify REPORT` for its tests and git). |
| `check` | `python3 dispatch.py check --claim "..." FILE` | Check a claim or draft against evidence. A `--claim` check is decided by its claim rows only; HAS_LEAKS, TIME_SENSITIVE and SELF_CONTRADICTORY print as advisory (OVERCLAIMS still blocks), since they judge an outbound letter, not a note. `ask --answer` and the pick trail run this check on the exact passage they save as evidence, and still refuse to auto-cache a TIME_SENSITIVE answer, but only when that label's own confidence is >= 0.80 -- a low-confidence TIME_SENSITIVE call is noise, not a finding, and no longer blocks a correct, fully-supported answer. |
| `verify` | `python3 dispatch.py verify REPORT` | Verify an agent's work report (git, tests, PRs, whether cited paths exist); it does not read cited files' contents, so use `check --claim "..." FILE` for facts. Contract, first output line is always `VERDICT: ...` and the exit code matches it: <br>1. Accepts one report file plus optional `--worktree` (git worktree of the protected repo), `--test-cmd` (a named test file), `--pr N`, `--dry-run`. <br>2. Outcomes: CLEAN 0, NO CHECKABLE CLAIMS 2, READ 3, REJECT 4, BAD USAGE 5, NEEDS SETUP 6 (worker-verify not installed), WORKTREE REFUSED 7 (nothing checked against it); `--dry-run` prints `DRY RUN - NO VERDICT`, exit 0. <br>3. Never CLEAN when any `CONTRADICTED_BY_FACT` row or refused evidence exists, dry run or real: a fact contradiction is REJECT, refused evidence is READ. <br>4. Requires the worker-verify door (and a Jev key for a real run); without the door it stops at exit 6, never a partial answer. |
| `help` | `python3 dispatch.py help --topic overview` | Quick Start and focused setup answers; no data, key, or Jev call needed. |

## Not connected yet?
Run `python3 ask.py --principal YOUR_AGENT --status` for scoped ready/stale/unknown sets, or `--preflight [--project-dir DIR] [--about "the work"] [--skill "what it does"]` before work: READY / WITH WARNINGS / NOT READY, connected files per folder, and (with --about/--skill) what is already known or already built.

A `preparation-required` result, an unknown pointer, or onboarding a new person/project is setup work, not "nothing found": see [`super-jev-connect/SKILL.md`](../super-jev-connect/SKILL.md). Check what you already have first: `YOUR_AGENT_NAME` is the agent's exact name: letters, digits, `.`, `_`, `-`, starting with a letter or digit, at most 64 (no spaces or slashes); any other name is refused.

```sh
python3 dispatch.py memory --principal YOUR_AGENT_NAME
```

## Live decision traces and Jev's voice

Every lookup (cache hits too, tier `cache`/`stale`) appends one redacted JSON line to `$STATE/traces.jsonl`: id, question, routing, content-check scores, final ranking, tier, timings, errors — never file contents or secrets. Rotates at ~20MB (one `.1` kept). `--approve` marks the last lookup for that question "right", `--miss` "wrong", `--add` after a miss "wrong, added". `ask.py --principal YOUR_AGENT --trace-report [--days 7]` reports right/wrong/unlabeled and top wrong questions. Each line also carries per-stage detail (cache, routing with Jev's none-probability, claim-mode word-search top 10 (BM25 per 3500-character passage, a file scores its best passage, two question words side by side in it count once more; a written phone number counts as "phone number"; a file under 0.55x the best not-yet-routed word score takes no read slot) and each file's fate, chunks/wording per content check, tie-break, final rule); `ask.py --principal YOUR_AGENT --trace-show <lookup_id|last>` prints it as plain lines to see where a file dropped out. `scorecard.py --principal YOUR_AGENT [--ask OLD/ask.py --ask NEW/ask.py]` grades a build on your own past questions for free (every `--approve`d or `--miss`ed question with its file becomes a saved test case): where the right file ranks in word search, and, given two builds, which cases the new one lost (exit 1). It replays only the free lexical helper; it does not measure ordinary semantic source retrieval. `shadow_repair.py` freezes one failure and controls, exports an isolated candidate patch or note proposal, and writes a bounded shadow comparison without deployment ([guide](references/shadow-repair.md)); missing held-out or paid evidence prevents acceptance. Reports tuned/held-out/retrospective splits separately; untagged history is retrospective. Reserve new held-out families before tuning with `--freeze-held-out FILE`, then verify using `--held-out FILE --held-out-sha256 PIN` ([reservation guide](references/scorecard-splits.md)); any held-out loss fails, regardless of gains. `paid_replay.py --principal YOUR_AGENT --cases FILE --ask OLD/ask.py --ask NEW/ask.py --max-asks N` replays a small case set through the full paid ask path (claim cases with `"kind": "claim", "expected": "TRUE"`) on a frozen copy of state and the memory backend (no saved answers, verdicts, reconnects or auto-heal; builds not declaring `REPLAY_PROTOCOL = 2` are refused), refuses to start over the cap, and calls a change inside the run-to-run wobble, an error, a timeout or input drift inconclusive.

When a lookup ends `OUTCOME: not-found`, the last line `ask.py` prints is exactly:

```
Super Jev: I didn't have this. Want me to find it by hand and save it for next time?
```

**A harness relaying `ask.py` output to a human must pass that line on verbatim.** Just above it, a miss prints `What was searched:` (connected sets, which had matches, files read with the closest named), then any `Skipped at setup` files that may hold the answer (reason and fix; apply the fix, do not reconnect the folder), and `Next step (pick one):` with exact commands, even when some pointer errored. Act on it instead of guessing: if the answer lives in a file you have, connect its folder with the printed `prepare_bulk.py` command; if you know the answer, save it with the printed `--add` command; otherwise tell your human it was not found and offer a by-hand search. A miss after reading files points to the filtering trace, not reconnecting those files. Abstract worth questions are not treated as monetary values. A hit marked `possible` is a lead, not an answer: open and check the file before using it.

## Maturity

Proven in current use: skill search, file-level `navigate`, checked connect, bulk prepare, `check` as a description gate, dataset and pointer listing, and the not-connected path. Experimental: passage-level `search`, saved-answer reuse (`approve`), and `verify` — treat their results as leads and read the evidence twice.

## Safeguards

`ready` is evidence, not an answer guarantee; review full support and original provenance before approval, and reuse an exact verified hit only within its returned scope. Preserve actual errors, uncertainty and missing preparation — a pointer error must never be hidden inside a "no candidates" reply. For transformed connectors, readable search paths and quoted line numbers refer to the reviewed view; upstreamPath is provenance only. Refresh replays the recorded policy and refuses raw downgrade ([view recipes](references/reviewed-views.md)). Connected means registered, not automatically synced; never invent a checked date or treat cache approval time as source freshness. No new access, privacy approval, execution permission, automatic syncing, or autonomous scheduler is granted here. Test/scratch output is never connected or word-searched when named `ops/sj*/...` (not `ops/sj-manual/`), `*superjev-test*` or `*-hand-test-*` (a file named exactly with `--name` is judged by its folder only, so a run log you name on purpose connects; the connect prints how many it skipped); save test reports under those names or outside connected folders so they can't come back as answers.

A pointer stuck `preparation-required`/`refresh-required` is just waiting on its own refresh, not a live failure — it's marked `[STALE]` in its line, its staleness never counts toward the sick-pointer circuit breaker, and it is never benched for it (a real provider error while routing it still counts, as for any pointer; a refresh landing mid-routing, `pointer-changed`, is asked again once). If every one of its files is already reviewed at its current bytes (nothing to redraft), the ask reconnects it before reading (no writer or Jev calls, one 45 s budget for all reconnects in the lookup; every attempt, failed or not, starts the pointer's 10-minute cooldown) and asks it again in the same lookup; a split part (`<pointer>-2`) heals through its parent's recipe. A file that really changed still gets the bounded background refresh (one at a time per agent; a pointer that finds one running is queued and refreshed right after it, cooldown and hourly cap still apply; the cap is shared fairly: a pointer over it waits in the queue, and one that already healed this hour queues behind any that is waiting). Until it lands, the set still answers: routing reads the catalog of its last refresh (memory `navigate` with `lastGood: true`; only the descriptions reviewed then reach Jev, and a deleted file is never a candidate), and word search reads the changed file's current text, so an edited note and every unchanged note stay findable. A changed file is read at its current text only as a refresh would admit it (secret, size, scope), and `--trace-show` marks it `edited since connect`; nothing is saved from it. Its line then reads `[pointer] stale: searched as of its last refresh (N file(s) changed since) ... [STALE]`, which is a note, not an error: it is not benched and never fails the exit code, but the OUTCOME line counts it as a set not fully searched (`partial`). A stale split part's line prints its parent's refresh command. A principal's own `<principal>-brain-root` pointer (its own brain) is never benched either, even after real repeated failures — it still shows its true status every call rather than a generic "benched" message. If its line says `auto-heal: last refresh FAILED: <reason>`, it will not heal on its own: fix the reason, then run the printed refresh command.

`ask.py --principal YOUR_AGENT --followup` re-tries pending misses and proposes a fresh top file for one-step `--approve` only when it's confirmed, isn't the exact file already named wrong, and actually shares subject terms with the question — a same-topic neighbor file (e.g. a different date's report in the same folder) can out-score everything on routing alone without being about what was asked, so it's never proposed.

## Banned patterns

Do not: treat "preparation required" as an answer; repeat a failed search instead of connecting or refreshing; say "your whole brain is connected" or "always up to date" without evidence of that exact capability; bury a pointer error under a "no results" summary; approve an answer without reading its evidence; wrap `ask.py`/`dispatch.py` in `timeout` (it is not available by default on macOS, so the call can die before Super Jev runs; use your harness's own time limit); fall back to a by-hand search because a call printed an error or nothing: inspect its exit status and stderr (poll it if still running, never start a second copy), fix the reported cause, then retry once; if still blocked, report it rather than loop.
