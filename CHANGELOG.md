# Changelog

## Unreleased

- The content check asks the plain question: "does this file state the answer to the question?" It used to ask whether the passage "supplies the requested fact or a necessary input", so a file about the right subject but without the requested property or a necessary input to it (for example a timeline for a question about a fact it never records) could pass on topic alone and be listed as found. Same single check, same number of Jev calls, no extra claim check; components and list items still qualify, and a file the check rejects is not reported as found (`ask.py` keeps only files that clear the source floor). Tests: `test/enhance/navigation.test.ts` ("source evidence asks whether the passage states the answer to the question").
- OUTCOME `found` counts ranked files only (at most five); skill suggestions get their own `N skill suggestions` label instead of being added to the file count. Tests: `skills/super-jev/tests/test_outcome_line.py`.
- Ordinary `ask` reads the files most likely to answer: word search runs again beside routing (routing scores only compare inside one pointer and see descriptions, so unrelated files could fill all five read slots and the note holding the answer was never read); the content check still decides what is kept
- An ask never waits on a refresh: every background launch in `auto_heal.py` (refresh, drain, scan) now starts through one helper with no inherited stdin/stdout/stderr and its own session, so a caller reading the ask's output to EOF gets it at once instead of waiting for the refresh (observed about 370 s). The refresh's own log is unchanged. Tests: `skills/super-jev/tests/test_auto_heal_never_wait.py`.
- Saved answers keep one promise. (1) One way in: `--approve`, `--answer`, `--used`, `--confirm-pick` and `--add` all save through one function (`save_answer`, with `add_manual` sharing its secret scan and claim check): CLEAN at 0.80 or higher against the cited file, and the secret scan; `--add` with no file gets the secret scan and is marked "no source file". The separate ungated approve paths and `find_pointer` are deleted. (2) Lifetime: a saved answer lasts until its source file changes; the 24-hour default (`cacheTtlSeconds` 86400) is gone (an operator may still set one), and a fact with no file lasts until it is marked wrong. A `--source` path that does not exist is refused (exit 2). A saved `--add` note whose source file changed after it was recorded is stale: the reply says so, the note is not ranked as current, and the question searches live. (3) One way out: `--miss` (wrong) removes the saved answer and exits 1 with "no saved answer" when there is none. (4) Matching: the same question after lowercasing, collapsing spaces and dropping trailing punctuation; nothing fuzzier; earlier saves are still found. (5) A hit prints "saved answer, from FILE, saved DATE" or "no source file". Tests: `skills/super-jev/tests/test_saved_answers.py`, `experiments/verified-pointer-memory/test_saved_lifetime.py`.
- Earn the Button: `build_cycle.py onboard` walks any new feature or file type through seven ordered steps (need, simplest rule, promise with Kelvin's approval, frozen dev/held-out cases with sha256, build with a SHIP review, prove, record), each leaving a checked artifact; `close` refuses an unearned onboarding. Tests: `skills/super-jev-build-cycle/tests/test_build_cycle.py`.
- `ask --claim` no longer lists a file the judge surely reads as not stating the statement (it used to print it under "Files found" beside a NOT FOUND verdict). Ordinary asks already drop a file the content check rejects and order by it; tests pin both. Tests: `skills/super-jev/tests/test_check_decides.py`.
- Connect keeps one small promise. It takes Markdown notes only (`--ext` and code/text connecting are removed); a note up to 250,000 bytes connects whole, a bigger one is held "too big, split it" (the section path for 250 KB to 2 MB notes from #246 and `--approve-held` are removed, with their tests). Every `prepare_bulk.py` run ends with `CONNECTED n, HELD m, FAILED k` and exits 0 only when m and k are 0 (1 if anything failed, 3 if anything was held), so a run that left files out no longer reads as complete; `refresh_changed.py` and auto-heal treat exit 3 as refreshed. A refresh of a pointer whose recipe recorded code suffixes is refused. `connect_checked.py` stays: `gate`, `gate_many` and `memory` are imported by `prepare_bulk.py`, `share_pointers.py` and `auto_heal.py`, and its hand-picked-list command is the only reviewed-view connect path. Tests: `skills/super-jev/tests/test_connect_promise.py`.
- Freshness: every heal attempt starts the pointer's cooldown, failed or not (a failing recipe replay used to retry on every ask). A report that records no principal is healed as the asking agent, which the refresh now records, instead of being skipped for good (`--asker-fallback` is gone); `refresh_changed.py` reports such a pointer as `needs-setup` with the one command to run. The hourly cap is shared fairly: a capped pointer waits in the queue, and a pointer that already healed this hour queues behind one that is waiting. `refresh_changed.py` opens with one outcome line (`fresh`, `refreshed`, `stale`, `needs-setup`, `error`) and exits 0, 0, 3, 2, 1. Tests: `skills/super-jev/tests/test_fresh_loud.py`.
- Ask output contract v2 (outcome line). Every ordinary `ask` now starts with exactly one line, `OUTCOME: found | not-found | not-supported | needs-setup | error`, with a short reason and, for every outcome but found, the one next command; it is computed from the whole search state (`found` with `partial: N sets not searched` when a set was stale or errored; `needs-setup` when nothing was found and a set was stale, unprepared or skipped, so a partial search is never a complete not-found). Exit codes match: found 0, not-found 1, not-supported 2, error 3, needs-setup 4 (`--claim` keeps its own). Replaced, not stacked: the stale-quiet drop of stale-pointer lines, the `unresolved: N of M pointers errored` line and the `no-candidates across` line are gone; per-file result lines stay. Notes over 12,000 characters (up to 250 KB) are now part of the contract: read in sections. The node chat CLI reads the OUTCOME line. Tests: `skills/super-jev/tests/test_outcome_line.py`.
- The secret scan holds only real secret values. A password/key keyword holds a file when a literal value follows it: a digit or symbol in it, a quoted word, or a single word of 4+ letters ending the line (skipping a short stop list: see, in, none, yes, no, demo, str, true, false, env, vault, null, todo, example, here, below, above), and it is not a placeholder (`<...>`, `$(...)`, `${...}`, `$NAME`) or a closed call. `password = self.password`, `api_key=...`, `apikey=demo` and `password: (moved to logins.md)` are no longer held. One placeholder list serves every keyword rule (`secret_patterns.json`, Python and Node). The blanket `--allow-held` flag is gone; a secret hold is never approvable (the fix is the rule, or removing the value); `--approve-held` stays for size holds.
- A content check no longer loses every file to one slow call. All files' checks share one Jev call, and navigation-cli gives that call one fixed timeout (`SUPERJEV_NAV_TIMEOUT_MS`, 15s) however many files ride in it, so a busy moment (live 2026-09-28: about 10 files in one call) timed out every file and the ask fell back to routing scores ("inconclusive: content check did not finish"). Now (1) a file that timed out in a shared run of 2+ files is checked once more on its own (one small call per such file, at most `SUPERJEV_NAV_CONCURRENCY` at once, the same payload judged by the same rules, so a finished check decides exactly as before); one that times out again stays inconclusive, other errors are not retried, and a run that held only one file is not sent again (a big file the token split already sent alone within a run of several is rechecked once, as the same call). The trace's `stages.timeout_rechecks` counts the rechecks. (2) Once every caller of a shared call has timed out, navigation-cli aborts that call instead of keeping the process open until its unused answer arrives (a 429/529 backoff wait ends early too, with no further call). The timeout itself and the token-based batch split are unchanged. Tests: `test_batch_jev.py`, `test/enhance/coalesce.test.ts`.
- Judge profile: the judge model's limits are stated once, in `skills/super-jev/judge_profiles.json` (window, questions per call, input price, endpoint and model, parts per direct check, confidence line, whole-file byte ceiling, Stop-gate window), and read by Python (`judge_profile.py`) and Node (`src/judge-profile.ts`), which derive the same numbers: input cap = window - 768, one call's budget = input cap - 2,000. One size unit, one function: every size check counts in judge tokens (UTF-8 bytes / 2, rounded up) through `judge_tokens` (Python) / `judgeTokens` (Node). The Stop gate's input cap and evidence window used to count characters / 4 against the same number the judge calls counted as bytes / 2, so number-dense text could pass the gate's cap and still go over the window; both now use the one function (the Stop-gate window default is 16,000 judge tokens, the same evidence size as its old 8,000 at chars / 4 for plain text). One selector: `SUPERJEV_JUDGE` picks the backend; `SUPERJEV_JUDGE_PROFILE`, the unused `question_kinds`, output price, label and `call_usd` are gone, an unknown profile name is an error, and a missing or broken table stops the run with one line. `SUPERJEV_INPUT_CAP_TOK` and `SUPERJEV_INPUT_USD_PER_MTOK` still override the cap and price. Tests: `test_judge_profile.py`, `test/judge-profile.test.ts`.
- Build cycle rules: step back after two FIX reviews (write why each fix failed, prefer a simpler fail-safe design); marks are honest grades (a saved fact and a tool crash are neutral, not helped or missed); refresh a PR's description to its final state before merge.
- Direct claim checks (`superjev.py gate`, `dispatch.py check`, build-cycle's check-report/review/reply-check with `--worktree` or `--evidence`) work in any shell where prose checks work, and never cut evidence. (1) A diff is judged as code by the built-in client in-process, which reads the key only from `TYPESAFE_API_KEY`; a shell whose key comes through a configured judge (`SUPERJEV_GATE_CMD`, as prose checks use) has none, and every diff check died with `TYPESAFE_API_KEY is not set -- export it first`. Now, with no key in the environment and `SUPERJEV_GATE_CMD` set, the check stays in code mode (the judgment-word refusal and the local pattern arm apply as before) and only the claims the pattern arm does not settle go to that judge, as evidence claims (`[reply:judge]` rows), with a note saying so; with the key set and a diff that fits one call, code mode is unchanged. (2) A direct check capped its evidence at `SUPERJEV_INPUT_CAP_TOK`, dropping whole older files and keeping the tail of the next with one warning that named none of them, so a big file pushed the others out and true claims about them came back NOT_SUPPORTED. Now only the Stop hook (which has a wall-clock budget) and `verify`'s extra `--paths` are capped, and their warning names every file dropped or cut. A direct check bigger than one judge call (bytes/2, as `lib/jev_client.py` counts) is split by the gate itself into parts, file by file and a too-big file at line breaks, nothing dropped; the judge runs once per part and the tables are merged (a contradiction in any part wins; a claim every part supports is SUPPORTED, as surely as its least sure part; a claim only some parts support is SUPPORTED_IN_PART, never CLEAN, with the parts that support it named, since no rule on a claim's words can tell one located fact from a claim about all the evidence ("eval is absent", "exclusively uses json.loads") that the part lacking the code supports; a red draft-level label in any part wins). Only masked evidence is split: when every file scans as a secret (nothing left after masking) the evidence goes whole, as before, and is refused, since a part of such a file can scan clean on its own. The output names the files in each part and the part behind each merged row; a part that errors makes the check that error, and a part the judge refuses without a table (exit 2, a quoted span it does not hold) is named and not judged, so the check is REJECT only when every part refuses and otherwise READ, never CLEAN; a part that exits 2 with a table keeps the check REJECT. When merging, a draft-level row with any label but its good one (NO_ANSWER too) is red, as the judge itself treats it, so a split check is never CLEAN where one call would say READ; in code mode such a row from the judge (outside the advisory ones) keeps the check from CLEAN too. Each part's own exit code is kept: the judge prints scores to 2 decimals, so from a part it flagged a SUPPORTED row printed at 0.80 is read as under the line (0.79), and a part flagged with no row saying why keeps the check READ. A check needing more than `SUPERJEV_MAX_PARTS` (default 40) judge calls is refused with nothing sent. Each part the judge sees opens with a note that it is part i of n and that a claim about the whole evidence cannot be supported from one part; checked live, the fleet judge contradicted "eval is absent from this diff" and "the diff is free of eval calls" on a 5-part diff. A keyword list for such claims was tried and dropped: every version missed wordings ("free of", "lacks", "zero", "removed", "exclusively") and a `--draft` check could only see the judge's 70-character echo of each claim. Line breaks in each `--claim` become spaces in the text sent to any judge (single call too); the pattern arm and judgment-word check still read the exact claim, and a verdict table repeating a row key is unreadable (ERROR): a line break in a claim echoed by the judge printed a forged `c2 SUPPORTED` row that replaced the real one. The Stop hook makes at most one judge call for a diff: a capped window needing more is not judged (advisory exit 3), never split. On the rerouted diff path a claim holding a secret is refused before the judge, and a missing built-in judge is the advisory exit 3 as before. A diff bigger than one call stays in code mode too, and its judge-bound claims are judged the same way, as evidence claims in parts, because the code question's "false" cannot tell a part that lacks the code from one that disproves the claim (keeping the best part said CLEAN for "no changed file calls eval" when one part did). Rows from parts are merged only when each part's c<N> is the same claim. Splitting in the gate means a configured judge that merges its own chunks differently (keeping its least sure chunk) is never handed more than one call. Tests: `test_superjev.py` (split, merge, contradiction, part error, cap naming), `test_noul_code_claims.py` (big diff judged in parts, a disproving part wins, key-less diff check through the configured judge), refused parts.
- A note written into an already connected folder is found without a hand reconnect. Before, only files in a pointer's list were refreshed: nothing marks a pointer stale for a file it has never seen, and 208 of the fleet's 233 prepare reports are legacy reports pinned to their file list, which `refresh_changed.py` skipped for new files and `prepare_bulk.py --refresh` never widened. In two 10-question tests (an Amazon-selling agent, a helper agent) several misses were notes written that week in connected folders. Now:
  - A legacy pinned pointer gets a one-time growth snapshot (`prepare-cache/growth/<pointer>.json`) the first time a scan or refresh looks at it with every root and pinned folder in place (none is taken while one is missing, so a restored folder cannot bring back files left out at connect). Those reports never recorded their `--exclude`, and neither the connect time nor a birth time (reset by a write-then-rename save) tells a file left out on purpose from a new one. So every connectable file then in a pinned folder but not in the list is listed as waiting, and joins only when a person checks it and runs `prepare_bulk.py --pointer NAME --principal AGENT --refresh --admit PATH`. After that, a file created after the snapshot directly in a pinned folder joins on its own, but only when the folder held no waiting file at the snapshot (or a person has admitted each one since), and only when no other pointer's files sit in that folder (compared by real path), so a note never lands in a pointer whose principals differ from its neighbours'. links.md and INDEX.md never join and never hold a folder back. No pointer whose root sits inside a vault folder (the 4 pinned medical pointers and the recipe pointer kelvin-medical-full, all under documents/) is ever listed or walked for new files, by the scan or by `refresh_changed.py`; changed files there still refresh as before (so kelvin-medical-full, a recipe pointer, still takes in new files when one of its files changes, as it did before this change), and a hand refresh lists no WAITING files for them. `setup.py --uninstall` removes `prepare-cache/growth/` (it names file paths) when it holds only snapshots. More than `--max-files` such files are not added (the #150 grown-root case is unchanged). `--admit` takes only WAITING files. A waiting file that was deleted keeps its folder closed (whatever left it out may still apply); the refresh says so, and a reconnect with `--root` rescopes. On the live cache (412 pinned folder entries across 208 legacy reports): 300 take in new notes on their own; 11 (57 files, including this week's Amazon notes) wait for a person, and `refresh_changed.py` prints them as `WAITING`; 67 are shared with another pointer and never take in new notes, with no message; 32 are the folders of 4 medical pointers whose roots sit inside documents/<person>/medical, and a folder inside profile/, documents/ or another vault folder anywhere on its real path never takes in new notes on its own (the inventory skips those parts only below a root; a person reconnects them by hand); 2 have a missing folder or root.
  - `refresh_changed.py` reports those new files, with one directory listing before any walk (and takes no snapshot on `--dry-run`).
  - Each ask starts a background scan of the asking agent's pointers, at most once per 10 minutes per agent (`SUPERJEV_NEW_FILE_SCAN=0` turns it off; never in a paid replay). It hands each pointer with a new file to auto-heal (same lock, queue, per-pointer cooldown and hourly cap). A queued one refreshes in the drain only if its file is still new, since a refresh reconnects and rotates approved answers.
  - A legacy report with no recorded principal is refreshed under the asking agent only while a new file is waiting (`--asker-fallback`, also re-checked in the drain), and that agent is not recorded. A changed file alone in such a report is still skipped ("no-report"), as before. The connect keeps every principal the pointer is registered for.
  - A new file that joined a pinned list but whose connect failed is kept as `unconnectedNew`; the pointer gets 3 tries in all for its unconnected files (one count per pointer, so a file that fails during another's last try gets fewer); after that they stay in the pointer's list, unconnected, until another refresh connects the pointer. A recipe pointer's failed new file is not retried this way (as before this change).
  - `refresh_changed.py` treats a pinned folder it cannot list as holding nothing new, instead of stopping (a folder it cannot enter at all still stops the older changed-file check, as before this change); a snapshot is also not taken while a pinned folder holds none of its listed files (a restore still filling it).
  - Every new or admitted file goes through `prepare_bulk.py --refresh`: secret scan and size holds, writer review, gate and connect check. The lookup that starts the scan does not wait on it; a later one finds the file. Tests: `skills/super-jev/tests/test_refresh_changed.py`, `test_prepare_bulk.py`, `test_auto_heal.py`, `test_stale_set_answers.py`.
- Checking claims against a diff that holds secret-shaped text no longer refuses the whole check. A worktree diff whose tests carry made-up secrets (a card scanner's fake card numbers, a redaction test's sample key) was refused ("the request contains a secret; not sent"), so such a change could not be checked from its own diff and agents fell back to hand-picked evidence files. Now `prepare_bulk.mask_evidence` judges all the evidence together, file by file: a file whose text scans as a secret (`has_secret`, real and fake values alike) anywhere in the evidence is withheld whole in every section (a worktree diff shows a file edited both in a commit and uncommitted twice; two patches can show it once each; a rename joins its old and new names; `diff --cc` sections count), keeping its clean `diff --git`/`---`/`+++` header and one line `[secret-shaped text: N line(s) withheld here; nothing in them can be checked]`; every other file goes to the judge as it is. A file section is read exactly as git writes it, hunks by the line counts in their `@@` lines; an evidence item that is not exactly git's diff output (a notes file, the tool output around a diff in the Stop hook's window, a hunk that ends before its counts) counts as one file, since any text in it may belong to any file in it; a build-cycle worktree diff never has such text. Evidence is read without newline translation (the gate, `jev_client.py`, and build-cycle's worktree diff), so a lone CR in a file stays inside its line instead of starting a fake `diff --git` line. Whole files, because the scanner finds where a secret starts but not where it ends: nine review rounds found part of a secret still sent by any narrower rule (a private key body before or after its BEGIN line or in a second hunk, a token or JWT signature wrapped or beside the match, the secret next to an AWS key id, a card's expiry and CVV, a value concatenated over lines). The promise is per file: a file's changes go out only when the scanner passes all of them; a secret cut into two files with no marker in the second is out of reach of any per-file scan, as before. A product file that itself holds secret-shaped text is withheld too, so the scanner's own comment example in `prepare_bulk.py` is now written as `<value>`; build such examples by concatenation, as the tests do. An evidence item left with nothing judgeable is dropped; the check is refused, as before, only when none is left. The gate masks before it cuts evidence down to its input cap, since a cut could drop a file's marker and leave the rest of it scanning clean. Used by the gate (`superjev.py gate`, code and evidence mode; the local pattern arm still reads the original, and claims it answers alone never need it) and by `lib/jev_client.py`; both name what they withheld (the gate's `--json` too, and its evidence-mode ledger entry), and a claim about it cannot be checked. Claims and drafts holding a secret are still refused, and `jev_client.ask()` keeps its full scan of every request.
- The secret scan now holds two card layouts it missed. (1) A card right after another digit group (`order 1234 4111 1111 1111 1111`): the card pattern never overlaps, so only the first 16-digit window of a grouped run was tested. Windows starting at a later group are now tested too when, in the same run, they have 1 to 4 digit groups before them and at most 4 after, of which at most 2 on each side have 4 or more digits (an order number, phone number or DD-MM-YYYY date before; an expiry and CVV after), pass Luhn and start with a card-network prefix (new `card_iin` pattern: Visa, Mastercard, Maestro, Discover, UnionPay, JCB, Diners, Mir). Cost, measured on random digits: a 20-digit number in groups of 4 is held 13 times in 100 instead of 10, a 24- or 28-digit one about 15 instead of 10; a phone number or date followed by a random 16-digit number 13 instead of 10; a 32-digit number in groups of 4 21 instead of 19; an all-digit IBAN such as a French one 13 instead of 10; a row of 10 or more 4-digit numbers exactly as before (19 in 100 for 10, 41 for 20: every first window is still checked). (2) A 15-digit American Express number (new `amex` pattern): starts 34 or 37, written 4-6-5 (`3782 822463 10005`) or 4-4-4-3 with one space or dash throughout, or compact, and passes Luhn; a random compact 15-digit number is now held about 2 times in 1000, and a Luhn-valid one starting 34/37 (an IMEI with that prefix, say) always. Python and Node, one pattern file. Nothing the old scan held is released. A USPS number standing alone on its line is held exactly as often as before: later windows are read with every check-digit-valid USPS run removed, so a card behind a 4- or 8-digit 91-95 group in exact USPS layout (`9100 4111 1111 1111 1111 01`) is still judged as before when the run's check digit happens to be valid (1 time in 10); holding those would hold about four times as many real tracking numbers. A USPS number followed by another short digit group (`... 3721 11 2 boxes`) is not exempt, as before, and is now held about 13 times in 100 instead of 10; so is a 20-digit Certified Mail number in groups of 4. As with 16-digit cards, text with any non-ASCII digit holds every Amex-shaped number without the Luhn check. Not covered: a card with 3 or more groups of 4+ digits before or after it in the same run (`order 1234 5678 9012 4111 1111 1111 1111`), 5 or more digit groups on either side, a card written in groups (space or dash) followed by `-MM-YY` (`4111 1111 1111 1111-12-27`: the ISO-date scrub removes `1111-12-27` first, as before), a card from a network not in `card_iin` (RuPay 60/81/82, Diners 39, Elo, Hipercard, Troy) after another digit group (held when it stands alone), 19-digit cards (UnionPay, Maestro, Visa, Mir: held only by chance, 1 in 10, when written 4-4-4-4-3, never when compact), cards written with dots (`4111.1111.1111.1111`, as before), 14-digit Diners cards, an Amex with mixed separators. Node: the overlapping scan runs on a regex copy, so a hit never leaves `lastIndex` on the shared pattern.
- A stale set no longer drops out of answers while its refresh cools down. Before, once a connected set's files changed and its refresh was cooling down (up to 10 minutes after the last one, longer while files kept changing), every ask skipped the whole set: routing refused it, so its unchanged notes were hidden along with the new one, and the only sign was a `preparation-required ... cooling down [STALE]` line and `unresolved: 1 of N pointers errored` at the bottom. The memory service's `navigate`/`navigate-many` take `lastGood: true` and route a stale pointer on the catalog it was registered with. Only the descriptions reviewed at connect reach Jev. The result carries `stale` (the files changed or missing since, taken again after the provider call, so an edit made while Jev routes still counts), a deleted file is never a candidate, and access and mid-navigation re-registration are checked as before. Without the flag, a stale pointer is still refused. `ask.py` always asks with it. A routed file that changed since is read at its current text only as a refresh would admit it (the same gate word search uses for edited files: reviewed at a known version and not failed by its last review, under the size ceiling, no secret, inside the recorded scope), and a claim it proves is never saved. The pointer's line reads `stale: searched as of its last refresh (N file(s) changed since)` with the auto-heal note, and it is no longer an error, so it does not add to `unresolved` or exit 1. Auto-heal, its cooldown and its hourly cap are unchanged: no extra refreshes. Tests: `experiments/verified-pointer-memory/test_last_good.py`, `skills/super-jev/tests/test_stale_set_answers.py`.
- build-cycle: start asks its history question ("what have we already tried, decided or learned about ...") about a short topic, not the whole idea. Before, the whole idea went into the question, and a 40-60 word idea made a long, blurry question that found fewer notes, less surely, than the same subject named in a dozen words. New `start "idea" --topic "the subject"` (at most 12 words); an idea of 12 words or fewer is its own topic, and a longer idea without `--topic` stops before any ask (exit 2) with the next step. The tool does not cut the idea itself: its first words are often not the subject. The whole idea stays in the receipt, the brief and the review brief; the receipt also records a topic given with `--topic` when it differs from the idea. A multi-line idea is kept on one line so brief and review-brief read all of it back.
- A spaced or dashed USPS tracking number no longer holds a notes file as card-like. A 22-digit number in groups of 4 (`9302 2110 4790 0005 3721 11`, made up) starts with a card-shaped 16-digit run, and about one in ten pass Luhn there, so one line held a whole 150 KB notes file. Before the card check (Python and Node, one pattern file, new `tracking` pattern), a whole digit run is removed only when it is written as a USPS IMpb number: starts 91-95, groups of 4 then a final 2 (22 or 26 digits), one space or dash throughout, valid GS1 mod-10 check digit, and no Luhn-valid 16-digit window starting at its 2nd or 3rd group (so a card behind a 4- or 8-digit 91-95 number, `9100 4111 1111 1111 1111 01`, is judged as before; about 1 in 100 real 22-digit tracking numbers, 1 in 50 for 26 digits, are therefore still held, down from 1 in 10). Everything else is checked as before: a card followed by a CVV or expiry, a card glued to a tracking number or to another number, a run with a wrong check digit or another prefix, length or grouping, and any text with non-ASCII digits (one such digit anywhere in the scanned text turns the exemption off for all of it). Left open: a card that itself starts 91-95 (no major network issues these), followed in the same layout by a 4-digit and a 2-digit group, or two 4-digit groups and a 2-digit group, reads as a tracking number one time in ten.
- Docs: `docs/AGENT-GUIDE.md` folded into `AGENTS.md` (preflight, remember-vs-one-off, claims, build cycle) and removed; README.md's quick start now just points to `docs/GETTING-STARTED.md` (people) and `AGENTS.md` (agents) instead of duplicating the commands.
- build-cycle v2: six required steps (preflight, start, check-report, review, reply-check, learn); target, cause, brief and prove become optional notes. start makes one ask (what we already know) plus `--ask` questions of your own, not four fixed ones. New `review-brief --worktree DIR` writes a self-contained brief (goal, diff, tests, what to try to break) for a fresh reviewer agent; `review` needs a verdict starting SHIP or FIX and a reviewer other than the builder, and close refuses while the latest review says FIX. start, review and reply-check cannot be skipped. super-jev SKILL.md says when to connect (search again) and when to check files directly (one-off); super-jev-connect SKILL.md says what is worth connecting.
- build-cycle: check-report, review and reply-check take `--worktree DIR` and/or `--evidence FILE`; the claims are then judged directly against those files and the worktree's diff (`dispatch.py check`, no connecting), because new code is not on Super Jev's shelves and a shelf lookup answered NOT FOUND for every claim about it. Without either flag the old shelf lookup is used.
- Reviewed oversized files stay connected. `prepare_bulk.py --approve-held PATH` (repeatable) admits one file held only for size, up to 1,000,000 bytes (bigger stays held with the split hint), after a person checked it, and records its path and sha256 in the pointer's report; `--refresh` and auto-heal replay the approval only while the file's bytes still match, and a changed file is held again with a reason naming the old approval. The approved file is read once and its hash verified before the writer, which gets exactly those bytes; the hash is checked again before the file is gated, cached and at the connect preview, so an edit made mid-run is held, never cached or connected. A file held for secret-like text or name is refused ("held for secret-like text; Super Jev never sends that text. Remove or move the value, then reconnect."), as are credential/key suffixes; `--allow-held` is unchanged and still never replayed. The secret scan (Python and Node, one pattern file) now treats a backslash-escaped quote before a placeholder (`KEY=\"$(cat file)\"`, `\"${VAR}\"`, `\'<...>\'` inside a code string) like a plain quote, so such code is no longer held (after an escaped quote only a closed `$(...)`, `${...}` or `<...>` of at most 200 characters counts as a placeholder, so a literal `\"$3cret9\"` or an unclosed `\"$(Secret9\"` is still held). A placeholder must now be the whole value, after an escaped quote, a plain quote or none: literal text glued after it (`"${VAR}hunter2xyz9"`) is held; before, the plain-quote form exempted any value starting with `$` or `<`; a real value after an escaped quote is still held.
- Tests: the secret-scan speed tests measure CPU time, not wall time, so a busy machine no longer fails them (a backtracking regex still does); the stale-quiet test looks for "benched", not "bench", so a checkout path containing "bench" no longer fails it.
- super-jev SKILL.md: never wrap ask.py/dispatch.py in `timeout` (not available by default on macOS; the call can die before Super Jev runs); an error or empty output means inspect exit status and stderr (poll a running call, never start a second), fix the cause and retry, or report it; not a by-hand search.

Recipes replay the selected suffixes and preserve supplied symlink roots across release switches. Code declarations provide best-effort passage headings with exact original line offsets; code is never executed and binary/control-character inputs are held before writing descriptions.

With `--about`, four asks (tried before, rules, traps, files) and NEW GROUND only when all four ran and none found a confirmed strong note (possible or inconclusive hits do not count; a failed or timed-out ask gives NEW GROUND UNKNOWN and a warning); coverage counts the files each ready pointer has registered now (the backend's source list, not a prepare report's approved list), walks symlinked folders like prepare does, and matches compound suffixes such as .schema.json; `--skill` searches for an existing skill first (a failed search is a warning, never "none"). - New skill `skills/super-jev-build-cycle/`: one standard-library tool, `build_cycle.py`, walks any agent that can run a shell through a build in ten steps (start, target, cause, brief, check-report, prove, review, reply-check) with Super Jev used inside each (`ask.py` lookups and `--claims-file`, `dispatch.py verify`, `--trace-show`), writing one receipt per step (`NN-step.md`) and one line per Super Jev call (`uses.jsonl`) in a cycle folder the user names. `skip STEP --reason` is recorded and shown at close. `close` exits 1 naming every missing step and every Super Jev use not yet marked helped, neutral or missed; otherwise it writes `summary.md` and appends one line per use to a log. - Questions that lead with a stance ask ("our take on X", "what's your view/opinion/thoughts on X", "what do we think of/about X", "how do we feel about X") are treated as opinion asks: the content check asks whether a passage answers the question instead of looking for an exact value, and a well-routed file the check rejects stays listed as possible. A question with a value cue (date, when, percentage, how much/many, number, amount, price, cost, total, deadline, share of) keeps exact-value wording. This only adds the new stance check; existing open-question handling is unchanged. Passage selection is unchanged, so a possible row means read the file, not a confirmed verdict.
- Manual-answer privacy checks compare decoded JSON strings, so quotes or backslashes in policy literals cannot evade the reviewed-view conversion guard.
- Auto-heal no longer starves a stale pointer behind the others. An ask heals its stale pointers in a fixed order, and only one refresh runs per principal, so the first changed pointer took the lock and a later one was skipped ("refresh already in progress") on every ask while the earlier ones kept changing; it could stay stale indefinitely. Now a pointer that finds the lock held is queued, and whoever holds the lock (a background refresh, an inline reconnect, including one that timed out, or a recipe replay) hands it to a drain that heals the queue one pointer at a time, oldest first, before it releases the lock (a connector pointer through its recipe, a pointer with nothing to redraft through the reconnect). Each still keeps its cooldown and the hourly cap; one it cannot run yet stays queued for the next refresh. Still never two refreshes for one principal at once, and no daemon: the drain is a short process that exits when the queue is done, and only a holder with the lock's token can release it. Every change to the lock file (take, reclaim a dead one, rename its owner, release) happens under one short per-principal file lock, so no check can interleave with another process's write. The lock now names the running refresh, not the ask that started it: after that ask exited, a refresh still running looked dead and the next ask could start a second one. The ask note says `another refresh in progress; queued to run after it`.
- `paid_replay.py` runs a free preflight before the first paid ask: each build's `ask.py --principal P --status` on the frozen state copy. It fails closed: unless every pointer a case could route to is listed as ready, it refuses (exit 2), naming the pointers and saying to reconnect or fix them first. That includes stale, error or unknown pointers, nothing connected, unrecognized or empty output, and a failed status. A replay never reconnects, so before this every case paid its asks and ended in the same error.

- New `paid_replay.py`: compares two builds on a small frozen case set (scorecard format; claim cases carry an expected TRUE/FALSE; a held-out row must match its frozen reservation exactly) through the full paid ask path, one `ask.py` subprocess per case and build (the question after a literal `--`, which `ask.py` now reads as the question even when it starts with `-`; a case question starting with `-` is refused, and a run whose trace is for another question or principal is inconclusive), under a required `--max-asks` cap it checks before the first ask. One snapshot of the principals' state (links followed; no saved claim verdicts, approvals or logs) and of the memory backend (answer database and registry, copied) is taken first, and every run gets a fresh copy of it. `SUPERJEV_REPLAY=1` makes `ask.py` skip saved answers, saved claim verdicts, stale-pointer reconnects and auto-heal; a build whose `ask.py` does not declare `REPLAY_PROTOCOL = 2` (all of these guarantees plus the literal `--` question) is refused before any ask, and a timeout kills the ask's whole process group. Both builds must read byte-identical prepare-caches; the report carries fingerprints, a cache that changes mid-run voids it (exit 3), and a case is inconclusive when the gold, or any file either run read, was not hashed before the pair (unpinned: every connected original, every file the prepare-cache names and the gold are hashed first) or changed from then to after it. A flip is inconclusive only when both the passing and the failing side sit within the run-to-run wobble (`--wobble`, default 0.10) of their line; errors, timeouts and saved answers are inconclusive; any other loss, or any held-out drop, exits 1.
- Scorecard reports tuned, held-out and retrospective cases separately, rejects known cross-split question/source-family overlap, and can reserve held-out cases in a new manifest verified against a pinned checksum. Any compared build losing a baseline-readable case fails, regardless of gains elsewhere. Untagged history stays retrospective; checksums do not prove unseen data.

- The description writer now sees a big file whole, not just its top.
