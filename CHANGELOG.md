# Changelog

## Unreleased
- Add an offline shadow repair runner: freezes scoped reviewed inputs and build code, compares one failure and controls through scorecard, exports a candidate patch/proposal and an explicit accept/reject report. Replay refuses unfrozen file reads, child processes and audited filesystem mutations, verifies the complete source/build inventory, and exports dependency changes. Baseline-readable controls and checksum-reserved held-out evidence are required. It never edits source notes or deploys; missing independent held-out or paid-stage evidence prevents acceptance.
- Scorecard reports tuned, held-out and retrospective cases separately, rejects known cross-split question/source-family overlap, and can reserve held-out cases in a new manifest verified against a pinned checksum. Any compared build losing a baseline-readable case fails, regardless of gains elsewhere. Untagged history stays retrospective; checksums do not prove unseen data.
- New `ask.py --principal AGENT --status` shows only that principal's registered connections, snapshot status and next steps, without a search or refresh.
- Claim checks retain read contradictory evidence for judgment instead of dropping it as an unanswered question. Abstract worth questions no longer automatically require an exact monetary value. Misses after reading files direct the caller to inspect the files and filtering trace rather than reconnect them.
- Explicit approvals record the caller principal instead of assuming a human approved them. Existing recorded approver labels are preserved; a cache entry without recorded identity displays unknown (legacy). Automatic check labels are unchanged.
- Explicit approval evidence preserves distinguishing dates and numeric identifiers when selecting a supporting line. Cache replay displays the best matching line from the saved reviewed quote, rather than truncating the passage opening before the proof; it does not fetch new source text or change approval status.
- A file named exactly with `--name` is no longer dropped by the test-output name rule (`*superjev-test*`, `*-hand-test-*`): it is judged by its folder only, at connect, in routing and in word search. Before, a run log connected on purpose (a `superjev-test-timeline.md` named in its pointer's `--name` list) was silently never connected or searched, so a claim it proves came back NOT FOUND. A named file inside a test/scratch or fixture folder still stays out, and a wildcard `--name` does not count. Connect now prints how many test/scratch files it skipped.
- `scorecard.py` grades the real ask code when an install keeps it as `ask_impl.py` behind a small `ask.py` launcher; before, the plain `scorecard.py --principal NAME` crashed on such an install (`no attribute 'prepare_bulk'`). A file that is not an ask module is refused by name. The skill page now says to name the file by its full path in `--miss`, since only a path makes the miss a scorecard test.
- New `scorecard.py`: grades a Super Jev build on the agent's own past questions, offline and with no Jev call. Every question answered from a file (`--approve`) or found elsewhere (`--miss` with the file) becomes a saved test case (`<state>/scorecard-cases.jsonl`, kept after traces rotate); `--cases FILE` adds hand-written ones. For each case it reports where the right file ranks in word search and whether it made the read slots; given two builds it lists the cases gained and lost and exits 1 when the new build loses one. All builds read the same prepare-cache, so a comparison measures code, not data. It replays the free word-search stage only.
- Word search gives a passage extra weight when it holds two question words side by side (a phrase such as "read the source" or "parent folder"), compared by their first four letters with stopwords skipped. Before, a file that stated the asked phrase could tie with files that only scattered the same words, and land one slot past the files that get read. No extra Jev calls; the read-slot count and floor are unchanged.
- A note edited since its pointer was connected stays findable while the pointer waits on its refresh: word search reads the file's current text instead of skipping it, held back only as a refresh would hold it (a secret, or over the size ceiling), and `--trace-show` marks it `edited since connect`. Before, an edited note could not be found at all until the background refresh finished, a whole cooldown if files kept changing. A stale split part (`<pointer>-N`) now prints its parent's refresh command; it printed "replaying its connect recipe failed", although parts refresh through their parent.
- The description writer now sees a big file whole, not just its top. It used to get only the first 15 headings and the first 1,200 characters, while the gate judges the whole file, so a long file whose content sits under one heading (this changelog, 37 KB, mostly under "Unreleased") was described by its oldest versions and refused. Past 15 headings, 10 more are taken evenly to the last; a file over 12,000 characters also gets 8 short passages (350 characters each, starting at a line start) spread across it. The addition is bounded whatever the file size. Small files, the built-in writer's quote (it still rebuilds identically), the writer's secret scan and the number of writer and gate calls are unchanged.
- A long file (over 14,000 characters) is read by section: its passages are cut at the line end nearest each 3,500 characters, not mid-line, and the content check reads the passages that best match the question's words (scored within that file, so a word on every page counts little), up to the same 14,000 characters. Before, fixed cuts could split one rule across two passages (super-jev/SKILL.md line 50), and the check always read the file's first passage plus the three sharing the most question words, so a big many-topic file (a changelog, a long log of past attempts) was often judged on the wrong sections. A passage after the first is sent led by the file's first line (its title), so a middle section keeps its subject. The listwise and claim steps show the same line-aligned passage. Same number of Jev calls and input size.
- `superjev verify` (and `dispatch.py verify`) passes `--pr`, `--base` and repeatable `--claim` through to the verify door; before, the wrapper rejected them although the door takes them, so a report's PR state could not be gathered. The quick-start help no longer says there is no automatic refresh (auto-heal refreshes changed pointers).
- `prepare_bulk.py`, `share_pointers.py` and `connect_github.py` check `--principal` against the same agent-name rule when parsing arguments, before building any state path from it (the memory runtime already refused to register such a name).
- A new agent's first ask (nothing connected) prints commands that run from any folder: the skill folder it was run from, not the repo-relative `skills/super-jev/...`, and the same for the not-set-up hint. When the fleet has a shared list (`shared-pointers.json`), it also names those sets and the one `share_pointers.py --principal NAME --shared` command that joins them without any connect.
- Agent names (`--principal`) must be letters, digits, `.`, `_` or `-`, starting with a letter or digit (at most 64). `ask.py` refuses anything else before touching state, and the memory runtime refuses to register it (connect and share). Before, a trailing space made a second, empty identity ("businessfi " beside "businessfi"), and a name such as `x/../primary` pointed its state folder at another agent's. That case was blocked only because no pointer was registered to such a name. Every name registered today already fits.
- The label writer's secret check scans the file text it sends, not that text's JSON form. JSON escaping turned a safe shell line such as `KEY="$(cat file)"`, which the setup scan admits, into a key=value hit. The writer then refused the whole batch, so every refresh of that pointer failed and it stayed stale. A real secret in the text or the checker feedback is still refused.
- A stale pointer whose last background refresh failed now says `auto-heal: last refresh FAILED: <reason>; retrying after cooldown` instead of the plain "refreshed recently, cooling down", which hid a refresh that kept failing.
- `ask --claim`: a line holding one word longer than the line window (a long URL containing a statement word) crashed the whole run (KeyError in the window count). Fixed. Also, a statement that fails to check now prints "could not be checked ... check it by hand" and the rest of a `--claims-file` still runs (exit 3, distinct from 2 for bad arguments), instead of one failure dropping every later statement.
- A stale pointer's printed refresh command names `prepare_bulk.py` in the skills folder the ask was run from (e.g. `~/.claude/skills/super-jev`), not the dated release folder it links to, which is gone after the next release. The printed folder is used only when it is the same folder as the running script (a link to it counts); an unrelated launcher's folder falls back to the real path.
- `ask --claim` offers Jev the lines that can prove the statement: all of a passage's lines (up to 2,000, was the first 60) are ranked and those sharing the most statement words fill the line budget first (shown in file order), and a long paragraph line is shown around its best-matching stretch instead of its first 160 characters. Before, a rule deep in a long markdown line never reached the line pick, so a TRUE verdict could quote a neighbouring line that did not show it. A verdict already in the claim cache keeps its old proof line until its file changes.
- A connected file is recorded at the path it was given (absolute, symlinks kept), with its real path alongside as `realPath`. Before, the connector resolved symlinks, so a skills folder linked to the current release was frozen at that release's copy: after each release the pointer kept serving old text and was never marked stale, because the old file never changed. Now a moved link makes the pointer stale and it refreshes. Duplicate checks and the sharing and audit path rules use both paths; auto-heal looks up the file by the given path. Takes effect on each pointer's next setup/connect: an existing pointer's saved recipe keeps the old resolved path until it is reconnected through setup.
- `ask.py --claims-file FILE` checks one statement per line (blank lines and `#` comments skipped), mixed freely with `--claim`: a draft's facts before sending, or a worker report's claims next to `dispatch.py verify REPORT` for its tests and git.
- Files up to 250,000 bytes connect (about 5 Jev calls to gate one). The label gate already splits evidence over Jev's input ceiling into parts and merges the verdicts, and the writer reads an excerpt, but setup still held every file over 90,000 bytes, so long notes logs, dead-ends lists and knowledge files were unsearchable unless split by hand. A part pointer now also closes early before the 5 MiB connect limit; with files under the old limit, parts are unchanged.
- `ask.py --claim "statement"` answers whether a statement is true by your own files. It runs the normal lookup on the statement; the listwise Jev call that already picks the best file also asks, per shown file, whether it supports, partly supports, contradicts or does not state the statement, and which of its lines shows it (a pick from the file's own lines). Plain code combines the per-file answers: TRUE/FALSE only at >= 0.90 with the proof file, date and line; files that disagree are a CONFLICT with the newest first; otherwise PARTIAL, UNSURE (read these files) or NOT FOUND in the files read. No extra Jev call. A sure TRUE/FALSE is saved per statement and dropped when its proof file changes. `--claim` repeats to check several statements in one run. Normal asks are unchanged.
- A split part that one of its principals cannot see no longer stays stale forever. A refresh asked only the first principal whether each part existed; a part registered for fewer principals than its siblings (never shared to one of them) looked new, was connected fresh and failed `already-connected` on every refresh and heal. Existence is now asked of every principal: the part refreshes in the scope it has, then widens to the connect's principals.
- A miss now names files setup skipped that may hold the answer, with the real reason and the fix: too big (split it, then re-run setup), held as password/card-like (review the flagged line, then re-run setup with `--allow-held`), or its label failed the check (re-run setup on that file). It reads only the principal's own `prepare-cache` reports and gate caches (a `-held.txt` list only when there is no report; a part pointer `<base>-N` reads its base only when the base is visible to that principal) and skips files that no longer exist. A too-big or secret-like file matches on its file name only (a secret-like file is never opened); a label-failed file also matches on its own text. A "writer returned no draft" file reads as its own reason. prepare_bulk now deletes `<pointer>-held.txt` when a run holds nothing, so a fixed file no longer reads as held. No provider call. When a skipped file is listed, the next step no longer says to connect its folder, which is already connected. A lookup where some pointer errored and nothing was found now prints the miss report too, not just the unresolved line.
- Sharing is opt-in per connection. Every connection is recorded private at connect time; `prepare_bulk.py --shareable` or `share_pointers.py --mark NAME` (a person's decision) marks it shareable, `--unmark` reverts, and a refresh or recipe heal keeps the mark. `share_pointers.py` refuses any unmarked pointer, so an agent folder not named `<bot>-brain` is no longer shareable by default; the brain/`documents/`/`profile/` check stays as a backstop and also blocks marking.
- Every agent can see the fleet's shared sets, not only its own brain. `share_pointers.py --principal AGENT --pointer NAME` (exact names) adds principals to an already-connected pointer through the memory `register` action: no reconnect, no writer and no Jev call. It refuses any pointer with a source under an agent's brain (`~/agents/<bot>-brain/`) or a `documents/`/`profile/` folder, so only fleet-wide sets are shared. Onboarding default: `<state dir>/shared-pointers.json` lists the shared sets (shared knowledge folder, skills catalog), and every fully connected `prepare_bulk.py` run shares them with its `--principal`s (`--no-shared` skips); `share_pointers.py --principal AGENT --shared` catches up an agent already connected. The recipe heal now retries with the registered principals on `scope-change`, as prepare_bulk already did, so a shared pointer still self-heals, and `audit-visibility` no longer flags a pointer on the shared list. Before, the shared knowledge folder was connected as a separate copy per agent, and most agents had no skills catalog at all.
- prepare_bulk never picks up git worktree copies: any `.claude/worktrees/` folder, or a checkout whose `.git` file points into another repo's `.git/worktrees/`, is skipped even when it is the `--root` itself (a submodule's `.git/modules/` file is kept). One agent carried 23 pointers of a Claude worktree's stale copy of its own brain. Takes effect on the next connect or refresh; existing copy pointers need a memory `remove`.
- "What steps / process / procedure ..." asks get the "does it answer" content-check wording instead of the exact-value one. A list of steps usually spans two or more passages, and the exact-value wording split Jev's pick across them, so the right skill file's best passage sat right at the confidence cutoff: "What steps does restart-seat-opus5 take to restart the supervisor seat?" ranked restart-seat-opus5/SKILL.md first on one run and dropped it for loop-job-opus5 on the next. `WHAT_ANSWER_RE` now also matches `step`, `steps`, `process` and `procedure`; value questions keep the exact-value wording, and plain fact lookups ("what model does the cron job run") are unchanged.
- Listwise step can now answer "none of these". It used to ask only which file was the single best answer and fell back to no opinion otherwise, so an on-topic lookalike stayed as a "possible" hit: "What are the steps in the restart-seat-opus5 skill?" returned loop-job-opus5, and a made-up CLOV verdict question returned history-recall/SKILL.md. The step is now one Jev choice call over the top 4 ranked files, each sent as the passage its content check scored best, plus "none of these files states the answer", with "Which file states the answer? When torn, pick none." A picked file moves to #1 (hub exemption unchanged) and is promoted to confirmed if its own probability is >= 0.9; only a strong (>= 0.9), unblocked pick demotes other confirmed files to possible. "none" at >= 0.9 drops every possible hit, so the ask reports not found when nothing confirmed is left; a weaker "none" keeps the files and prints "Jev leans none of these" so the agent decides. It still costs one call and fails open. `SUPERJEV_LISTWISE=0` turns it off. The trace stage `listwise` records the pick and what it dropped.
- A real run's STATUS.md under `ops/sj*/` is visible again (e.g. `ops/sj-fleet-onboard-2/STATUS.md`, the outcome of a real onboarding run); every other file there, and every file in a bench/eval/test run folder (`ops/sj-retrieval-bench/`), stays hidden. Takes effect on the next connect or refresh of the pointer.
- A plain `fixtures/` folder or an `evidence/<...>/sources/` folder counts as test material only under a test or docs folder (`test/`, `tests/`, `__tests__/`, `spec/`, `e2e/`, `docs/`, `examples/`, `bench/`), so a lighting business's `fixtures/` or a legal case's `evidence/` is no longer hidden. `__fixtures__/`, `__mocks__/`, `testdata/` and `sample-data/` still count on their own.
- Fixture, sample and evidence-source folders never rank as answers. A made-up sample about another company (`docs/evidence/<run>/sources/Engineering/Deployment/releases.md`) came back as the answer to "What decision was made about releasing Super Jev v1.0.22?". `is_test_material` now also matches `fixture(s)/`, `__fixtures__/`, `__mocks__/`, `testdata/`, `test-data/`, `test_data/`, `sample-data/`, `sample_data/` and any `sources/` folder under an `evidence/` folder, and routing (step 3) now drops test material the same way it drops bench datasets; connect and word search already skipped it. Takes effect on the next ask; a pointer that already holds such files keeps them connected but they never rank.
- A file the cover gate demotes is dropped, not kept as "possible". Capping it at 0.84 still returned history-recall/SKILL.md as a possible hit for a made-up question about Kelvin's CLOV verdict; a file that holds almost none of the question's words (coverage under 0.2) is now dropped, and the route-keep and big-file keeps skip it too, so the answer is "not found".
- Word matching is Unicode- and accent-aware. The word pattern matched only plain a-z, so accented words were cut up ("papá" -> "pap", "¿Cuántas" -> "cu" + "ntas", "niño" -> "ni" + "o") and short pieces were dropped, which weakened word search ranking, the cover gate's coverage and the routing prefilter for every non-English user. All of them now share one tokenizer (`words()`/`fold()` in ask.py): Unicode letters and digits, case- and accent-folded, so "papa" and "papá" match. ASCII text tokenizes exactly as before. Common Spanish question words are stopwords like their English ones. Saved pointer words (`pointer-words.json`) carry a tokenizer version and rebuild on their own at the next ask; no other stored index uses the tokenizer.
- A file no longer reaches the confirmed tier while holding almost none of the question's words. A one-passage file is judged as that passage against "none", so a short, on-topic-looking file could pass the 0.85 content check for an event it never names: a made-up question about Kelvin's CLOV verdict confirmed history-recall/SKILL.md, which holds only "kelvin" and "last". After the content check and listwise promote, a confirmed file whose idf-weighted coverage of the question's words (the same weights word search uses) is under `CONFIRM_MIN_COVER` 0.2 is capped at 0.84: possible at most, and dropped on value questions, which have no possible tier. A file word search never indexed gets no opinion. The trace stage is `cover_gate`.
- prepare_bulk now drops cache entries outside the current scope on every run (an old `--root`, a narrowed `--exclude`/`--name`). Before, a refresh only dropped entries whose file was gone from disk, so after a pointer moved from a /tmp stage to `~/.claude/skills` the still-existing /tmp entries stayed in `prepare-cache/<pointer>.json`, and word search, which reads that cache as the pointer's file list, kept returning files that were no longer connected. `allowTargets` is now recorded as full paths, so a relative `--allow-target` replays the same folder from any working directory.
- Connecting `~/.claude/skills` in place crashed with `KeyError` part-way through (parts 1-2 registered, 3-6 left on the old copy): a skill whose SKILL.md is a symlink came back from the connect preview under its target's real path, and prepare_bulk looked its hash up by the path it sent. It now matches preview paths on realpath, as ask.py and auto_heal already do. `--name` now matches case-insensitively (`--name SKILL.md` also takes `skill.md`, the name most fleet skills use). A `--refresh` given a new `--root` no longer inherits the old root's `--no-recurse`, which silently skipped every nested file under the new root. A symlinked file is now judged on its target too: the target must sit under a `--root` or a `--allow-target DIR` folder (repeatable, recorded and replayed on refresh) and pass the same name, folder (profile/, documents/, hidden) and secret-name checks, so a link can no longer pull in logins.md or a profile/ file.
- Connecting a skills folder no longer needs a flattened copy: routing (step 3) sees only each file's name and description, and every skill's entry file is named SKILL.md, so a pointer of skills showed Jev 50 leaves all called "SKILL.md", and a recursive connect of the folder took in every reference doc (920 files against the 250 cap). The workaround was to copy the files into a temp folder as `<skill>__SKILL.md`, which is wiped on reboot and stales the pointer. Now a flat catalog leaf whose file name is shared with another source in the same connect is labelled with its parent folder too (`ebay-return-label/SKILL.md`); unique names are unchanged. `prepare_bulk.py --name GLOB` (repeatable, e.g. `--name SKILL.md`) keeps only matching file names, and is recorded in the recipe so `--refresh` and `refresh_changed.py` replay it. Takes effect on the next connect or refresh of a pointer.
- "Which skill/tool/command ..." asks: the answer is a SKILL.md in the trusted skill roots, which are not connected files, so these asks returned the connected doc about skill search as "possible" for unrelated skills. ask.py now also runs the skills connector (`dispatch.py skills`, one Jev call, in parallel with routing) for such questions and prints its picks first as `skill  <SKILL.md>  [skills: <name>]`. Every principal gets this with no connect step. `SUPERJEV_SKILLS=0` turns it off. The trace stage is `skills`.
- A stale pointer nothing can refresh (no prepare_bulk report, no connect recipe, or a replay that failed) prints its error once per day per principal instead of on every answer, and the other sightings log `stale-quiet` to lookups.jsonl. A pointer that is healing still shows every time. The refresh hint only prints a prepare_bulk command for a pointer prepare_bulk built.
- Stale connector pointers self-heal: a pointer connected through the path connector (memory `connect`, connect_checked, connect_github) rather than prepare_bulk had no recorded recipe, so when one of its files changed auto-heal skipped it as "no-report" on every ask and the hint printed a prepare_bulk command that cannot rebuild it (prepare_bulk reads only .md files). Connect now records its own request (paths, descriptions, structure, principals) as `recipe` in the dataset registry; a new memory action `recipe` reads it even while the pointer is stale (principal-checked; a path-connected dataset from before this change gets one rebuilt from its prepared manifest). A stale pointer with no prepare_bulk report is reconnected inline from that recipe at its files' current bytes (local only, no writer or Jev call, the connector's secret scan still runs; per-pointer cooldown after a success) and read in the same lookup. A dataset built by hand (neither recipe nor path connection) is reported as needing one reconnect through the connector instead of a prepare_bulk command that fails.
- Saving uses ask()'s own evidence: `--answer`, `--approve` (top, `--rank`, `--file`), `--confirm-pick` and the pick-trail flush used to fetch their evidence ticket through memory `search`, a second, weaker ranking (file descriptions only, top 3, no word search or listwise). A file ask() ranked #1 could fail to save with "search returned no-match" (businessfi GEICO pending-asks note). They now cite the file ask() ranked (or the lead picked) directly: a new memory `open` action records an attempt with no retrieval (needs `allowAgentAssist`, like `assist`), `assist` cites the file's opening line plus its line that best matches the answer, and the claim check runs on exactly that cited passage. Kept: the check gate (only CLEAN at >= 0.80 saves), the confident TIME_SENSITIVE refusal, the secret hold and the stale-file check; a question already saved under any pointer (a manual `--add` too) is reported as already cached, never overwritten. `search` stays only as the fallback when no file is known (`--approve` with an explicit pointer) or on an older runtime without `open`.
- Pick trail: a refused pick (TIME_SENSITIVE/REJECT/CONTRADICTED/stale/secret-held) used to be dropped from `pending_picks.jsonl` with only a transient print during the automatic every-5-picks flush, so it vanished from `--pending-picks` with no lasting trace beyond `lookups.jsonl` -- a correct, "fair" refusal looked identical to a silent bug. It now stays in the file tagged `"dropped": <reason>` and lists under a "Dropped (not saved)" section in `--pending-picks`, cleared only by an explicit `--confirm-pick` or `--drop-pick` (being shown does not clear it). (businessfi hand test, 2026-09-25)
- Auto-cache time-sensitive override now requires a confident call: `ask.py --answer`'s gate re-check turned a CLEAN verdict into TIME_SENSITIVE off the raw label alone, ignoring the confidence riding next to it, so a near coin-flip call (label TIME_SENSITIVE at 0.05-0.10 confidence -- jev's own 0.80 "read the source, act on neither answer" line not cleared) was blocking a fully-supported, correct answer. The override now only fires when that label's own confidence is >= 0.80, matching the floor jev uses everywhere else for a call worth acting on. (health-fitness hand test 7)
- Listwise reorder hub exemption (h22, 2026-09-25 fair head-to-head): a hub/copy/write-up file (README/INDEX/PROFILE/`_staging`/pr-history) that wins the listwise call no longer moves back above a non-hub file already ranked ahead of it. `prefer_sources` already demotes a hub below a confirmed or higher-scored note in its folder; the listwise reorder had no matching exemption (unlike the near-twin tiebreak, which already sits hubs out), so it could win the pool and un-demote the hub straight back to #1. Repro: gustavo/medical/README.md (0.98, on-topic index) outranked the confirmed 2026-04-09-panel.md (0.91) because listwise picked the README. Documented, not fixed: two held-out recall misses (h16, h17) where the gold ops-report file was never routed as a candidate by any pointer -- both files are indexed and reviewed; the miss is Jev's own routing judgment on a thin, generic description, not a code bug, so no code fix was made (see superjev-ask-path.md's routing section).
- Listwise reorder + promote: after content check, one extra Jev call runs over every file that reached the possible tier (>= 0.60), asking which single one best answers the question. The winner moves to #1 of the final ranking, never demoting anything else, and is promoted to confirmed (>= 0.85) only if its own winning probability is itself >= 0.9. A failed, timed-out, or "none of these" call leaves today's order and scores unchanged (fail open). `SUPERJEV_LISTWISE=0` turns it off. Tested against the installed baseline and a separate AND-gate variant on the same question set (`superjev-tests/listwise-2026-09-25/result.md`, "Version C"): Improved on internal eval (details kept private). Cost: +1 Jev call on the ~80% of asks where a file reaches the possible tier at all. Two runs per version against a comparable noise floor -- a real gain, not a clean settled one; see the result.md verdict.
- Batched Jev calls: routing for every pointer runs in one navigation-cli process whose Jev questions share calls (new `navigate-many` memory action), and every file's content check rides one run the same way. Each question is still answered on its own, so labels and scores mean the same; a batch over the input budget is split automatically, and an over-ceiling reply splits it again. `SUPERJEV_BATCH_JEV=0` goes back to one call per pointer/file. Full eval, same-day data, live (no caches): Jev calls per ask 25.0 -> 3.8, seconds per ask 10.0 -> 5.8. Improved on internal eval (details kept private).
- Claim check size guard counts estimated tokens instead of characters: number-dense evidence under the old 110,000-character cap could still overrun Jev's ceiling and fail. Evidence too big for one call is now split into parts, each checked on its own and merged (a contradiction or red draft-level label anywhere wins; otherwise a claim any part supports is SUPPORTED).
- Word search scores each file by its best 3500-character passage instead of the whole file, so a long note (the 36 KB medical timeline) is no longer sunk by its unrelated visits; a written phone number (212-305-6390) counts as the words "phone" and "number"; a file under 0.55x the best not-yet-routed word score takes no read slot. Improved on internal eval (details kept private). Fixes "NYP ENT phone number" (hand test 6).
- Stale pointers: when every file of a stale pointer is already reviewed at its current bytes (auto-heal used to skip it as "no-change" forever, e.g. primary-reference), the ask reconnects it inline with `--no-findability` (no writer or Jev calls; one 45 s budget for all reconnects in a lookup, then left running in the background; no cooldown after a failed or timed-out reconnect) and reads it in the same lookup. Split parts (`<pointer>-N`) now heal through the parent's report instead of skipping as "no-report". Real changes keep the background refresh.
- Content check, spread answers: among files in the same tier, a file read as several passages ranks on its best passage plus half the on-topic probability the other passages took (`file_score`, SPREAD_CREDIT 0.5), so a note whose answer spans passages outranks a sibling with one slightly stronger passage. Tiers still come from the best single passage (possible >= 0.60, confirmed >= 0.85; blend capped at 0.84); live-value asks get no blend. No extra Jev calls.
- Routing cost: a pointer is not routed when a question of 2+ words has none of them (or a listed synonym: doctor/physician, dad/father, car/vehicle...) in any of its files. Never skipped: a pointer holding a resolved person's folder, or one whose files cannot be listed. Words are read locally via `sources` beside routing, once per pointer generation (`$STATE/pointer-words.json`); word search still searches every pointer.
